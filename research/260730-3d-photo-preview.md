# 3D 空間に写真を浮かべて選ぶプレビューアプリ — 技術調査

調査日: 2026-07-30 / 対象: photo-orb M1

## 1. やりたいこと

ローカルフォルダの写真が 3D 空間に浮遊し、見回して 1 枚を選ぶ。
「一覧をスクロールする」体験ではなく「空間の中から見つける」体験を作る。

## 2. 3D レンダリング手段の比較

| 手段 | 良い点 | 難点 | 判定 |
|---|---|---|---|
| **Three.js + @react-three/fiber** | React の状態と 3D シーンが同じ書き方で繋がる。ホバー/クリック判定(Raycaster)が `onPointerOver` / `onClick` として提供される。drei に OrbitControls などの部品が揃う | 依存が増える。R3F v9 は React 19 必須 | ✅ 採用 |
| 生 Three.js | 依存最小。挙動が完全に見える | シーンの追加/削除を自前で命令的に管理する必要があり、写真リストが動的に変わるアプリでは破棄漏れ(テクスチャリーク)を作りやすい | ❌ |
| Babylon.js | エディタ・物理・PBR が最初から強い。TypeScript ネイティブ | ゲーム寄りで写真板を並べるには過剰。React 統合が薄い | ❌ |
| CSS 3D transform (`transform-style: preserve-3d`) | 依存ゼロ。`<img>` そのままなので画像品質が良い | 遮蔽(z-fighting)とライティングが破綻する。数十枚で合成負荷が跳ねる。「浮いている空間」の説得力が出ない | ❌ |

**バージョン確認（2026-07-30 時点の npm latest）**

- `three` 0.185.1
- `@react-three/fiber` 9.6.1 … v9 系は React 19 対応版。React 18 だと v8 系が必要
- `@react-three/drei` 10.7.7 … R3F v9 対応系
- `electron` 43.2.0 / `electron-vite` 5.0.0

## 3. 球殻上に均等配置するアルゴリズム

素朴に緯度経度を等分割すると極付近が密集する（メルカトル歪みと同じ問題）。
**Fibonacci sphere（黄金角スパイラル）** が定番の解。

```
i 番目 (N 個中):
  y   = 1 - 2i/(N-1)              … y を -1..1 に等間隔 → 帯ごとの面積が等しい
  r   = sqrt(1 - y²)              … その緯度での半径
  θ   = i × 2π × (1 - 1/φ)        … 黄金角 ≈ 137.5°。有理数比にならないので周回しても重ならない
  x,z = r·cos θ, r·sin θ
```

- 計算量 O(N)、乱数不使用なので**同じ写真集合なら毎回同じ配置**になる（再現性があり、テストも書ける）
- 極付近が密になりすぎない。植物の葉序（ひまわりの種）と同じ原理

M1 ではこれを純関数 `sphereLayout(count, radius)` として renderer から切り離し、単体テストを置く。

## 4. Electron でローカル画像を安全に配信する

`file://` を renderer に直接読ませるのは避ける（`webSecurity` を緩める必要が出る）。

採用: **カスタムプロトコル + 使い捨てトークン**（既存 mascot-editor の `mascot-media://` と同方式）

```
renderer が受け取る URL:  photo-file://p/<uuid>
main が持つ対応表:        uuid → 絶対パス（dialog を通ったフォルダ配下のみ）
```

- renderer は実パスを一切知らないため、パストラバーサル（`../../etc/passwd`）が**構造的に**成立しない
- Windows のドライブレターや日本語ファイル名の URL エンコード事故も起きない
- `protocol.registerSchemesAsPrivileged` は `app.whenReady()` より前に呼ぶ必要がある（モジュール読込時に実行）
- 特権は `standard` / `secure` / `stream` のみ。`supportFetchAPI` は付けない（用途は `<img>` 相当のテクスチャ読み込みだけ）

> スキーム名に `photo` 単体を使わない: 将来 OS 側で予約される可能性を避け、`photo-file` とする。

## 5. テクスチャ読み込みとパフォーマンス

| 論点 | M1 の判断 | 将来 |
|---|---|---|
| 読み込み待ち | 写真 1 枚ごとに `<Suspense>` を張り、読めた順に空間へ現れる。全枚数を待たない | プログレス表示 |
| 原寸ロード | 4000×3000 の JPEG を 60 枚 = VRAM 数 GB になり得る。**M1 は表示枚数に上限（60 枚）** を設ける | main 側で sharp によるサムネイル生成 → 選択時のみ原寸 |
| ミップマップ | Three.js 既定で生成。遠景の写真がちらつかない | 非 2 冪テクスチャの扱いは WebGL2 なら問題なし |
| テクスチャ破棄 | R3F の `useTexture` はアンマウント時に dispose される | フォルダ切替時のキャッシュ管理 |

## 6. 選択インタラクション

- ホバー: R3F の `onPointerOver` / `onPointerOut`。カーソルも `document.body.style.cursor` で変える
- クリック: `onClick`。イベントは最前面のメッシュから順に伝播し、`e.stopPropagation()` で背後の写真への貫通を止められる
- 「手前に飛んでくる」演出: 選択されたカードを **カメラ前方の一点へ lerp 移動**させ、姿勢をカメラの `quaternion` に合わせる
  - 別案（カメラ自体を写真の前へ動かす）は、OrbitControls の target と競合して制御が絡む。**カードを動かす方が状態が 1 箇所に閉じる**
- 選択中は OrbitControls を無効化（見回しと拡大表示の操作衝突を防ぐ）
- 解除は再クリック / Esc

## 7. M1 のスコープ外（将来）

- VR/XR（WebXR）対応 — R3F なら `@react-three/xr` で乗せられる
- ドラッグ&ドロップでのフォルダ投入
